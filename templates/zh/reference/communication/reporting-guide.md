# 报告与升级的方法

> **必须**：在报告与升级之前，确认 `communication/message-quality-protocol.md` 的必填项目。

向上司报告是组织运作的生命线。
通过以适当的时机和形式进行报告，支持问题的早期发现与快速决策。

## 工具的使用区分

报告使用 `send_message` 工具。请遵守以下约束。

| 工具 | 用途 | 备注 |
|--------|------|------|
| `send_message` | 向上司、同事进行一对一报告、提问 | 报告、进度、请求判断用 `intent="report"`，提问用 `intent="question"`。Anima 名、别名、`slack:`/`chatwork:` 等（参见下文） |
| `post_channel` | 向整个团队发布通知（Board） | acknowledgments、感谢、FYI 使用 Board。同一频道 1 run 1 次。run 之间没有 cooldown |
| `call_human` | 向人类发送紧急通知 | 服务停止、安全事件等 |

**send_message 的约束**：
- `intent` 为必填，值**只能是 `report` 或 `question`**（报告、进度用 `report`，提问用 `question`）。**`delegation` 不能在 `send_message` 中使用**（工具会拒绝）。任务委派使用 `delegate_task`
- 同一 run 中向同一收件人发送的 DM 最多 1 条。收件人数量没有上限
- 追加联络使用 Board（post_channel）
- **收件人**参见下文「收件人的解析」（Anima 名、人类别名、直接指定 `slack:` / `chatwork:` 等）
- **注**：在聊天会话中，不能向人类使用 send_message。请直接用文本回复

### 收件人的解析与外部投递（`core/messaging/outbound.py`）

`send_message` 的 `to` 按以下**优先级**解析为内部 inbox 或外部（Slack / Chatwork）。空字符串无法解析，会报错。

1. **与已知 Anima 名完全一致**（区分大小写）→ 内部 inbox。已知列表为 `~/.animaworks/animas/` 直下的目录名
2. **与 `config.json` 的 `external_messaging.user_aliases` 的键一致**（别名**不区分大小写**）→ 外部投递。`external_messaging.preferred_channel`（`slack` / `chatwork`）为 `slack` 时，若有 `slack_user_id` 则用 Slack，若无则有 `chatwork_room_id` 则用 Chatwork。`preferred_channel` 为 `chatwork` 时优先 `chatwork_room_id`，若无则有 `slack_user_id` 则用 Slack。**两个 ID 都没有**的别名会报错（需在 `external_messaging.user_aliases` 中设置联系方式）
3. **`slack:USERID`**（开头为 `slack:`，后续为 Slack 用户 ID）→ 直接发送到 Slack DM（USERID 在实现上**规范化为大写**）
4. **`chatwork:ROOMID`**（开头为 `chatwork:`，ROOMID 部分仅去除前后空白）→ 直接发送到 Chatwork 房间
5. **Slack 用户 ID 单独**（`U` + 英数字**8 个字符以上**，匹配时允许大小写。例 `U0123456789`）→ 直接发送到 Slack DM
6. **与已知 Anima 名不区分大小写一致** → 内部（规范化为磁盘上的正式名称）
7. 均不匹配 → 未知收件人错误（工具层在聊天执行中与其他情况下提示文案可能不同）

**外部相关配置**（`config.json` 的 `external_messaging`）：

| 字段 | 作用 |
|-----------|------|
| `preferred_channel` | 别名收件人的默认频道（`slack` / `chatwork`） |
| `user_aliases` | 别名名 → `{ "slack_user_id": "...", "chatwork_room_id": "..." }`（**至少需要一方**） |

**外部发送的行为**（`send_external`）：

- 尝试顺序为**先发送已解析的频道**，失败则尝试**另一个频道**（仅当别名等同时具备 Slack、Chatwork 两方的收件人 ID 时才有第二个。直接指定 `slack:` / `chatwork:` 通常仅该频道）
- 因外部频道未配置等原因无法发送时，工具结果可能以 JSON 返回 `NoChannelConfigured` 或 `DeliveryFailed`
- 正文会**从 Markdown 转换为 Slack mrkdwn / Chatwork 格式**
- **Slack**：若存在与 Anima 名关联的 `SLACK_BOT_TOKEN__{anima名}`（Vault 或共享 credentials），则用 Bot 令牌发送，并附加显示名（Anima 名）和**图标 URL**（来自 Anima 资产）。**若无 Bot 令牌**，则在正文开头加上 `[送信者Anima名] ` 后发送
- **Chatwork**：使用发送 Anima 自身的 identity 令牌（`CHATWORK_API_TOKEN__<Anima名>`）。经 `send_message` 时正文开头会加上 `[Anima名] ` 前缀

**发送上的行为**：

- 没有按时间、按天的发送预算，也没有因对话深度而拒绝发送。
- 内部 Anima 之间的深度可能为诊断目的被记录，但消息会照常投递。

## 报告的时机

### 需要即时报告的场合（MUST）

以下场合，应在认识到发生时立即向上司报告：

| 场合 | 理由 | 例 |
|------|------|-----|
| 任务完成 | 上司据此判断下一步行动 | 部署完成、报告编写完成 |
| 错误、故障发生 | 为了早期应对 | API 停止、检测到数据不一致 |
| 需要判断的场合 | 请求超出自己权限的决定 | 方针变更提案、资源追加请求 |
| 截止日期延迟已确定 | 上司据此调整日程 | 因阻塞导致工作停止 |
| 安全上的担忧 | 需要立即处理 | 非法访问的征兆、认证信息泄露嫌疑 |

### 定期报告的场合（SHOULD）

| 场合 | 频率 | 内容 |
|------|------|------|
| 每日总结 | 每天（业务结束时） | 当日成果、次日计划 |
| 每周回顾 | 每周（周五） | 一周的成果、课题、下周计划 |
| 长期任务的中途进展 | 酌情（参考：每 2-3 天） | 进度率、剩余工作、有无阻塞 |

### 无需报告的场合

- 记忆的写入、整理（内部工作）
- 例行工作无异常时（心跳中相当于 `HEARTBEAT_OK`）
- 上司明确指示「无需报告」的工作

## 报告的基本格式

### SCANA 格式

报告由以下 5 项构成。无需包含全部项目，可根据情况取舍选择。

| 项目 | 英语 | 说明 | MUST/MAY |
|------|------|------|----------|
| 状况 | Situation | 现在发生了什么 | MUST |
| 原因 | Cause | 为何如此（在已查明的情况下） | MAY |
| 应对 | Action taken | 自己采取的应对 | SHOULD |
| 下一步 | Next steps | 今后做什么 / 希望判断什么 | MUST |
| 附加信息 | Appendix | 相关日志、文件路径、数值 | MAY |

### 回复时的线程延续

回复上司的消息时，指定 `reply_to`（回复目标消息 ID）和 `thread_id`（线程 ID）以维持对话上下文。ID 格式为 `YYYYMMDD_HHMMSS_ffffff`（例：`20260215_093000_123456`）。

```
send_message(
    to="manager",
    content="承知しました。15時までに対応します。",
    intent="report",
    reply_to="20260215_093000_123456",
    thread_id="20260215_090000_000000"
)
```

### 格式使用示例

```
send_message(
    to="manager",
    content="""【完了報告】売上データ月次集計

状況: 2026年1月の売上データ集計が完了しました。
対処: 部門別・カテゴリ別に集計し、前月比も算出しました。
次のステップ: 特にアクション不要です。レポートをご確認ください。
付加情報: /shared/reports/sales_summary_202601.md""",
    intent="report"
)
```

## 按报告类型的模板

### 完成报告

任务正常完成时的报告。

```
send_message(
    to="manager",
    content="""【完了報告】{タスク名}

状況: {タスク名}が完了しました。
成果物: {ファイルパスまたは結果の要約}
所要時間: {かかった時間}
備考: {特記事項があれば}""",
    intent="report"
)
```

**具体示例：**

```
send_message(
    to="manager",
    content="""【完了報告】API仕様書のv2.1更新

状況: API仕様書にv2.1の変更点を反映しました。
成果物: /shared/docs/api-spec.md（差分: セクション3.2, 4.1を更新）
所要時間: 約45分
備考: ページネーションの例を3パターン追加しました。""",
    intent="report"
)
```

### 错误报告

发生故障或错误时的报告。

```
send_message(
    to="manager",
    content="""【エラー報告】{何が起きたか}

状況: {現在の状態の説明}
原因: {判明している範囲での原因}
影響範囲: {何が止まっているか、誰に影響しているか}
対処: {自分が試した対策とその結果}
次のステップ: {今後の対応案 / 判断が必要なこと}""",
    intent="report"
)
```

**具体示例：**

```
send_message(
    to="manager",
    content="""【エラー報告】定期バッチ処理の失敗

状況: 毎朝9:00のデータ同期バッチが3回連続で失敗しています。
原因: 外部APIのレスポンスタイムアウト（30秒超過）。API側の障害の可能性が高い。
影響範囲: 今朝以降のデータが未同期。ダッシュボードの数値が昨日時点で止まっている。
対処: タイムアウトを60秒に延長して再実行 → 同様に失敗。API提供元のステータスページを確認 → メンテナンス情報なし。
次のステップ: API提供元への問い合わせが必要です。ご判断をお願いします。""",
    intent="report"
)
```

### 请求判断（决策的升级）

自己权限内无法判断时的报告。

```
send_message(
    to="manager",
    content="""【判断依頼】{何について判断が必要か}

状況: {現在の状況}
選択肢:
A. {選択肢Aの内容} — メリット: {利点} / デメリット: {欠点}
B. {選択肢Bの内容} — メリット: {利点} / デメリット: {欠点}
私の推奨: {A or B}（理由: {なぜ}）

ご判断をお願いします。""",
    intent="report"
)
```

**具体示例：**

```
send_message(
    to="manager",
    content="""【判断依頼】ログ保存期間の変更

状況: ディスク使用量が85%に達しており、1週間以内に90%を超える見込みです。
選択肢:
A. ログ保存期間を90日→30日に短縮 — メリット: 即座に50GB削減 / デメリット: 古いログでの調査が不可能に
B. ストレージを追加（500GB） — メリット: ログを維持できる / デメリット: 月額コスト増（約$50/月）
C. 古いログをアーカイブストレージに移動 — メリット: ログ維持+コスト抑制 / デメリット: 実装に2日必要
私の推奨: C（コストとデータ保全のバランスが良い）

ご判断をお願いします。""",
    intent="report"
)
```

### 中途进展报告

长期任务的中期报告。

```
send_message(
    to="manager",
    content="""【途中経過】{タスク名}

進捗: {完了した作業 / 全体に対する進捗率}
残作業: {まだ終わっていないこと}
ブロッカー: {あれば記載。なければ「なし」}
見込み: {期限に間に合うか}""",
    intent="report"
)
```

**具体示例：**

```
send_message(
    to="manager",
    content="""【途中経過】ユーザー通知機能の実装

進捗: Phase 1（設計）完了、Phase 2（実装）の70%が完了
  - メール通知: 完了
  - Slack通知: 完了
  - アプリ内通知: 実装中（残り1日程度）
残作業: アプリ内通知の実装 + テストコード作成
ブロッカー: なし
見込み: 期限（2/20）に間に合います。""",
    intent="report"
)
```

- {あれば記載}

■ 明日の予定
- {予定1}
- {予定2}""",
    intent="report"
)
```

### 具体示例

```
send_message(
    to="manager",
    content="""【日次サマリー】2026-02-15

■ 完了したこと

## 紧急报告 vs 普通报告的判断

### 紧急报告（即时，MUST）

符合以下情况时，即使中断其他工作也要立即报告：

- **服务停止**：对用户产生影响的故障
- **数据丢失、损坏**：可能变为无法恢复的状态
- **安全事件**：非法访问、信息泄露嫌疑
- **截止日期延迟已确定**：已承诺的截止日期确定无法赶上

紧急报告的消息 MUST：在开头加上「【紧急】」。
服务停止、数据丢失、安全事件等需要人类即时应对时，也应同时使用 `call_human`。

```
send_message(
    to="manager",
    content="""【緊急】本番データベースの応答遅延

状況: 本番DBの応答時間が通常の10倍（平均300ms→3000ms）に悪化。
影響: Web UIのページ読み込みが10秒以上かかる状態。
対処中: スロークエリの特定を開始。10分以内に続報します。""",
    intent="report"
)
```

### 普通报告（在下次心跳或每日总结中）

以下紧迫性较低，可以汇总报告：

- 按计划推进的任务的中途进展
- 轻微问题且已自行解决的事项
- 改进提案或想法

## 升级判断流程图

判断是否应升级报告的步骤：

```
1. 自分の権限内で解決可能か？
   → Yes: 自分で対処し、完了後に結果を報告
   → No: ステップ2へ

2. 緊急性はあるか？（サービス影響・データ損失リスク）
   → Yes: 【緊急】として即座にエスカレーション
   → No: ステップ3へ

3. 判断の選択肢を整理できるか？
   → Yes: 選択肢と推奨を添えて【判断依頼】として報告
   → No: 状況をありのまま報告し、上司の指示を仰ぐ
```

## 报告中的注意事项

### 应做的事（MUST/SHOULD）

- MUST：在 `send_message` 的 `intent` 中指定 **`"report"`（报告、进度）或 `"question"`（提问）**。`"delegation"` 不可（委派用 `delegate_task`）
- MUST：区分事实与推测来写。推测需加上「可能性很高」「大概」等
- MUST：明确影响范围。「什么」对「谁」产生影响
- SHOULD：包含自己尝试的对策及其结果。避免上司提出相同对策的浪费
- SHOULD：自己主动提出下一步行动。不要等待指示

### 应避免的事

- 把结论放在后面、从经过开始长篇书写（结论先行）
- 只有「出问题了」而没有具体信息的报告
- 将多个不同话题汇总到一条消息中（按话题分开）
- 隐瞒问题或试图淡化问题（传达准确状况）
- 在同一 run 中向同一收件人发送多条 `send_message`（向同一收件人发送最多 1 条。收件人数量没有上限）
