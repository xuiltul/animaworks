# 层级间的规则

在 AnimaWorks 中，Anima 之间的沟通存在基于组织层级的规则。
本文档定义各种关系（上司、部下、同僚、其他部门）中的规则。

## 基本原则

- 组织内的所有往来均通过 `send_message`（消息传递）进行
- 禁止直接共享内部状态。用自己的语言进行压缩、解释后传达
- 每条消息都必须明确目的。必须包含“希望对方做什么”“想传达什么”

## 与上司的沟通（报告、联络、咨询）

上司是在 `supervisor` 字段中指定的 Anima。
显示在系统提示词的“上司”栏中。

### MUST（义务）

- 任务完成时必须报告结果
- 作业过程中发生问题或阻塞时，必须迅速报告
- 需要超出自己判断范围的决策时，必须咨询
- 对上司的指令理解不明确时，必须确认

### SHOULD（推荐）

- 长期任务应报告中间进度
- 报告问题时，应一并传达“发生了什么”“尝试了什么”“建议”
- 报告应简洁。需要详细信息时，应写入文件并发送引用

### 消息示例

任务完成报告:
```
bob宛: APIエンドポイントの実装が完了しました。
- GET /api/users — ユーザー一覧取得
- POST /api/users — ユーザー新規作成
- テストも全件パス済みです。
次のタスクがあればご指示ください。
```

问题报告:
```
bob宛: DB接続でタイムアウトが頻発しています。
- 発生: 本日14:00頃から
- 試したこと: コネクションプールのサイズ拡大（改善せず）
- 推測: 同時接続数が上限に達している可能性
- 提案: コネクションプールの最大値を50→100に変更してよいか確認したいです。
```

决策咨询:
```
alice宛: キャッシュ戦略について判断をお願いしたいです。
- 選択肢A: Redis導入（高速だがインフラコスト増）
- 選択肢B: ファイルキャッシュ（低コストだが速度に限界）
- 私の推奨はAですが、コスト面の判断はお任せします。
```

## 监督者工具

拥有部下的 Anima 会自动启用用于组织管理的专用工具。

### 工具列表

| 工具 | 对象范围 | 概要 | 主要参数 |
|--------|---------|------|----------------|
| `org_dashboard` | 全部下属（递归） | 以树形显示全部下属的进程状态、最后活动、当前任务、任务数 | 无 |
| `ping_subordinate` | 全部下属（递归） | 确认下属是否存活。省略 `name` 时全体一并确认，指定时仅确认单个 Anima | `name`（可选） |
| `read_subordinate_state` | 全部下属（递归） | 读取下属的 `state/current_state.md` | `name`（必填） |
| `delegate_task` | 仅直属部下 | 原子性地注册完整的执行输入与追踪引用，并通知部下 | `name`, `instruction`（必填）, `summary`, `acceptance_criteria`, `workspace`, `model`（可选） |
| `task_tracker` | 自己的委派任务 | 从下属侧队列追踪通过 `delegate_task` 委派的任务进度 | `status`（可选: "all"/"active"/"completed", 默认 "active"） |
| `audit_subordinate` | 全部下属（递归） | 生成活动时间线或统计摘要。省略 `name` 时对全部下属一并审计（整合时间线） | `name`（可选）, `mode`（可选: `"report"`/`"summary"`, 默认 `"report"`）, `hours`（可选: 1〜168, 默认 24）, `direct_only`（可选: boolean）, `since`（可选: `"HH:MM"` 当天的开始时刻，指定时优先于 hours） |
| `disable_subordinate` | 全部下属（递归） | 让下属休眠（status.json enabled=false，约30秒后进程停止） | `name`（必填）, `reason`（可选） |
| `enable_subordinate` | 全部下属（递归） | 恢复已休眠的下属 | `name`（必填） |
| `set_subordinate_model` | 全部下属（递归） | 请求 root 更新 status.json，并 reload 正在运行的主模型 | `name`, `model`（必填）, `reason`（可选） |
| `set_subordinate_background_model` | 全部下属（递归） | 请求 root 更新用于 Heartbeat/Cron 的后台模型。从下次后台任务起应用，用空字符串清除 | `name`, `model`（必填）, `credential`, `reason`（可选） |
| `restart_subordinate` | 全部下属（递归） | 重启下属进程（restart_requested 标志，约30秒后重启） | `name`（必填）, `reason`（可选） |

`check_permissions` 可供所有 Anima 使用（确认自己的权限列表）。

### 任务委派流程

1. 执行 `delegate_task(name="dave", instruction="目的・成果物・制約・期限・必要な文脈", acceptance_criteria=["確認可能な完了条件"])`。
2. 完整的输入与追踪引用被原子性地注册到正规任务存储中。
3. Worker 确认依赖关系与空闲容量，获取可执行的任务。
4. 通过 DM 通知 dave。DM 不是执行输入，不应作为重新生成缺失任务的材料。
5. 自己的委派追踪条目是对同一任务的引用，而不是另一个可变副本。
6. 用 `task_tracker(status="active")` 追踪进行中的委派任务（`status="all"` 查看全部，`status="completed"` 仅查看已完成）

### 下属状态确认（应定期进行）

```
org_dashboard()                        # 配下全体の状態をツリー表示
read_subordinate_state(name="dave")    # dave の現在タスクと保留タスクを確認
ping_subordinate()                     # 全員の生存確認
audit_subordinate(name="dave")         # dave の直近24時間の活動タイムライン
audit_subordinate(name="dave", mode="summary", hours=168)  # dave の直近7日間の統計サマリー
audit_subordinate()                    # 全配下の統合タイムライン（直近24時間）
audit_subordinate(direct_only=true)    # 直属部下のみの統合タイムライン
audit_subordinate(since="09:00")       # 全配下の今日9時以降の統合タイムライン
audit_subordinate(name="dave", since="13:00")  # dave の今日13時以降
```

#### audit_subordinate 的模式

| 模式 | 输出内容 | 用途 |
|--------|---------|------|
| `report`（默认） | 时序时间线。按事件显示图标、时刻、内容。工具使用在底部汇总 | 把握“今天做了什么” |
| `summary` | 事件数、任务状况、通信对象、错误详情的统计显示 | 定量评估活动 |

省略 `name` 且对象为多个 Anima 时，`report` 模式会生成将所有 Anima 的事件按时序合并的 **整合时间线**。

### 组织扩展（创建新 Anima）

持有 `skills/newstaff/SKILL.md` 的 Anima 可通过 `create_anima` 工具创建新 Anima。
指定角色表（`character_sheet_content` 或 `character_sheet_path`），
创建后会自动注册到 config.json，并通过服务器重新加载使其生效。
省略 `supervisor` 时，调用方的 Anima 会被设置为上司。

## 与部下的沟通（指令、确认）

部下是显示在系统提示词“部下”栏中的 Anima。
所有将自己设置为 `supervisor` 的 Anima 均属于此列。

### MUST（义务）

- 下达任务指令时必须包含以下内容:
  - **目的**: 为什么需要这个任务
  - **期望的成果物**: 制作什么、做什么
  - **成果物路径**: 委派对象自己的目录或 `common_knowledge/`（不可指定自己的 `knowledge/` — 部下无法写入）
  - **截止日期、优先级**: 何时之前、有多紧急
- 收到部下的完成报告后，必须反馈确认结果
- 必须定期用 `org_dashboard` 确认下属状态

### SHOULD（推荐）

- 应考虑部下的 speciality 来分配任务
- 指令应具体。应避免模糊表达（“做得差不多就行”）
- 有多个部下时，应先整理任务依赖关系再下达指令

### MAY（可选）

- 为促进部下成长，可以分配稍有挑战性的任务
- 需要部下之间协作时，可以明确相关人员后下达指令

### 消息示例

任务指令:
```
dave宛: ユーザー認証APIの実装をお願いします。
- 目的: フロントエンドからのログイン機能を実現するため
- 成果物: POST /api/auth/login エンドポイント（JWT返却）
- 仕様: メールアドレス+パスワードでの認証。失敗時は401を返す
- 期限: 今週金曜まで
- 関連: eve がフロントエンド側のログイン画面を並行で作成中です。
  API仕様の質問があれば eve と直接やりとりして構いません。
```

确认、反馈:
```
dave宛: 認証APIの実装、確認しました。
- ログイン・ログアウトとも正常動作を確認
- 1点: トークンの有効期限が設定されていないようです。24時間で期限切れにしてください
- それ以外は問題ありません。修正後に再度報告をお願いします。
```

## 与同僚的沟通（协作、协调）

同僚是拥有相同 `supervisor` 的 Anima。
显示在系统提示词的“同僚”栏中。

### SHOULD（推荐）

- 应与负责相关业务的同僚直接往来
- 自己的工作会影响同僚工作时，应事先共享
- 共同作业时，应明确各自负责什么

### MAY（可选）

- 可以就同僚的 speciality 相关知识进行咨询
- 可以请求评审或意见

### 消息示例

协作请求:
```
eve宛: 認証APIの実装が完了したので共有します。
- エンドポイント: POST /api/auth/login
- リクエスト: { "email": "...", "password": "..." }
- レスポンス: { "token": "JWT文字列", "expires_in": 86400 }
- エラー時: 401 { "error": "Invalid credentials" }
フロントエンド側のログイン画面で使ってください。質問があればいつでもどうぞ。
```

咨询:
```
carol宛: 管理画面のUIについて相談したいのですが、
ユーザー一覧画面のテーブルレイアウトについて、
20列以上のカラムがあるのですが、どう表示するのが良いでしょうか。
あなたのUXの観点からアドバイスいただけると助かります。
```

## 与其他部门成员的沟通

其他部门是指拥有与自己不同 `supervisor` 的 Anima。
未显示在同僚栏中的 Anima 属于此列。

### MUST（义务）

- 原则上不得直接联系其他部门的成员
- 需要与其他部门协作时，必须向自己的上司说明
- 经上司联系对方部门的上司，再由那里向对方下达指令

### 沟通路径

例: dave（bob 下属）想联系 frank（carol 下属）时

```
正しい経路:
  dave → bob(自分の上司) → alice(共通の上司) → carol(frankの上司) → frank

間違い:
  dave → frank（直接連絡は禁止）
```

### 消息示例

向上司的请求（需要其他部门协作时）:
```
bob宛: 顧客データのエクスポート機能について、
営業部の frank さんが必要とするCSVフォーマットの詳細を知りたいです。
carol さん経由で確認していただけますか？
```

### 为什么避免直接联系

- 上司将无法把握业务全貌
- 指令系统会混乱，存在发出矛盾指令的风险
- 各部门上司将失去判断优先级的机会

## 顶层 Anima 与人类的联络

未设置上司（supervisor）的顶层 Anima 负有直接联系人类管理者的职责。
联络使用 `call_human` 工具。

### MUST（义务）

- 检测到问题、错误、故障时必须用 `call_human` 联络
- 需要超出自己判断范围的决策时必须报告
- 部下上报的事项中自己无法解决时必须报告

### SHOULD（推荐）

- 重要任务完成时应报告
- 对部下的业务状况有担忧时应报告

### MAY（可选）

- 定期巡查中未发现特别问题时可以不报告
- 轻微的自动修复完成时可以不报告

### 消息示例

问题报告:
```
call_human:
  subject: "本番環境のAPI応答遅延を検出"
  body: |
    14:00頃からAPIの応答時間が通常の3倍に増加しています。
    - 影響: ユーザー向けAPIの全エンドポイント
    - 試したこと: コネクションプールの状態確認（異常なし）
    - 推測: DBサーバーの負荷が高い可能性
    - 提案: DBサーバーのスケールアップを検討してください
  priority: high
```

决策请求:
```
call_human:
  subject: "新機能リリースの承認依頼"
  body: |
    ユーザー認証機能の実装が完了し、全テストがパスしました。
    本番環境へのリリースについて承認をお願いします。
  priority: normal
```

## 紧急时的异常规则

通常的层级规则有以下异常。

### 紧急事态的定义

符合以下情况时，可以作为“紧急事态”适用异常规则:

- 正在发生系统故障或服务停止
- 正在发生安全事件
- 上司长时间不响应的状态持续
- 截止日期临近，按通常路径来不及

### 紧急时允许的行动

- 可以直接联系其他部门的成员（但事后必须向上司报告）
- 可以越过上司，直接联系其上级上司（但事后也必须向直属上司报告）
- 可以自行做出通常需要咨询的决策（但事后必须报告并获得批准）

### 紧急联络的消息示例

```
frank宛: 【緊急】dave です。通常は上司経由ですが、緊急のためご連絡します。
本番環境でユーザーデータの不整合が発生しています。
営業側で顧客から問い合わせが来ていないか確認していただけますか？
bob と carol にも同時に報告しています。
```

向上司的事后报告:
```
bob宛: 【事後報告】本番障害の対応で、frank さん（carol配下）に直接連絡しました。
- 理由: 顧客データ不整合の影響範囲を緊急確認する必要があった
- 対応内容: frank さんに顧客からの問い合わせ状況を確認依頼
- 結果: 3件の問い合わせが来ており、frank さんが対応中
事後報告となり申し訳ありませんが、ご確認をお願いします。
```

## 规则优先级总结

| 优先级 | 规则 | 分类 |
|--------|--------|------|
| 1 | 向上司的问题报告、上报 | MUST |
| 2 | 任务完成的报告 | MUST |
| 3 | 向部下的指令中包含目的、成果物、截止日期 | MUST |
| 4 | 禁止直接联系其他部门 | MUST |
| 5 | 与同僚的直接协作 | SHOULD |
| 6 | 中间进度的报告 | SHOULD |
| 7 | 紧急时的异常适用 | MAY |
