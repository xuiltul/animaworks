# 지시 전달 방법 패턴 모음

> **필수**: 위임 지시 전에 `communication/message-quality-protocol.md`의 필수 항목을 확인할 것.

부하나 팀 멤버에게 명확하고 실행 가능한 지시를 내리기 위한 패턴 모음.
모호한 지시는 재작업과 혼란의 원인이 된다. 이 가이드에 따라 상대가 망설임 없이 행동할 수 있는 지시를 하도록 하자.

## 도구별 사용 방법

| 도구 | 용도 | 비고 |
|--------|------|------|
| `delegate_task` | 직속 부하에게 작업 위임 | 작업 큐에 추가하고 DM 전송. 진행 상황은 `task_tracker`로 추적 가능. 직속 부하에게만 사용 가능 |
| `send_message` | 일대일 요청·보고·질문 | `intent` 필수: `report` 또는 `question` 중 하나. 부하에게 작업을 위임할 때는 `delegate_task` 사용. 사람 별칭을 받는 사람으로 지정하면 외부 채널(Slack/Chatwork 등)로 전달 |
| `animaworks-tool board post <channel> <text>` | 전체 공유(공지, 해결 보고) | 확인·감사·FYI는 Board 사용. `@名前`로 멘션 가능(멘션 대상에게 DM 알림). 자세한 내용은 `board-guide.md` 참조 |
| `animaworks-tool internal manage-channel <action> <channel>` | 채널 ACL 관리 | 채널 생성·멤버 추가·삭제·정보 확인. 제한 채널 운영 시 사용. 자세한 내용은 `board-guide.md` 참조 |

**send_message의 제약**:
- `intent`은 필수. `report` / `question`만 허용. 확인·감사·FYI는 `animaworks-tool board post <channel> <text>`로 Board에 공유할 것. 부하에게 작업을 위임할 때는 `delegate_task` 사용
- 동일한 run에서 동일한 수신자에게 보낼 수 있는 DM은 1건까지. 수신자 수에는 제한 없음
- 옵션: `thread_id`(스레드 ID), `reply_to`(답장 대상 메시지 ID)로 대화 스레드 유지 가능

**Board 게시 CLI의 제약**:
- 채널 멤버여야 함(ACL). 제한 채널의 경우 멤버가 아니면 게시 불가
- 재게시 쿨다운이나 DM / Board 공통 전송 예산은 없음

## 명확한 지시의 5가지 요소

지시를 내릴 때 다음 5가지 요소를 포함할 것(MUST). 상대의 확인·재작업을 최소화한다.

| 요소 | 설명 | MUST/SHOULD |
|------|------|-------------|
| 목적(왜) | 이 작업이 필요한 이유·배경 | MUST |
| 기대 성과(무엇을) | 완료 시 무엇이 완성되는가 | MUST |
| 마감일(언제까지) | 작업 완료의 마감일 | MUST(긴급하지 않아도 기준 시점을 제시) |
| 제약·조건(어떻게) | 사용해야 할 방법, 피해야 할 것 | SHOULD |
| 보고 시점(언제 보고) | 완료 시 / 중간 경과 / 문제 발생 시 | MUST |

## 좋은 지시 vs 나쁜 지시

### 예시 1: 데이터 집계 요청

**나쁜 지시:**
```
send_message(
    to="alice",
    content="売上データを集計しておいてください。",
    intent="question"
)
```
문제점: 어떤 데이터인지, 어떤 기간인지, 어떤 형식으로 출력할지, 언제까지인지가 불명확. 부하에게 요청이라면 `delegate_task`를 사용할 것.

**좋은 지시:**(부하라면 `delegate_task` 사용. 동료·비부하에게 요청은 `intent="question"`)
```
send_message(
    to="alice",
    content="""売上データの月次集計をお願いします。

目的: 経営会議（2/20）の資料として使用
対象: 2026年1月の売上データ（/shared/data/sales_202601.csv）
成果物: 部門別・製品カテゴリ別の集計表（Markdown形式）
出力先: /shared/reports/sales_summary_202601.md
期限: 2/18（火）17:00まで
報告: 完了時に結果サマリーを返答してください。""",
    intent="question"
)
```

### 예시 2: 조사 작업 요청

**나쁜 지시:**
```
send_message(
    to="bob",
    content="APIのエラーについて調べておいて。",
    intent="question"
)
```
문제점: 어떤 API인지, 어떤 오류인지, 조사의 깊이, 보고 형식이 불명확. 부하라면 `delegate_task`를 사용할 것.

**좋은 지시:**
```
send_message(
    to="bob",
    content="""GitHub API のレート制限エラー (HTTP 403) の調査をお願いします。

背景: 昨日15時頃から断続的に発生しており、自動デプロイが失敗している
調査してほしいこと:
1. エラー発生の頻度とパターン（ログ: /var/log/deploy/github-api.log）
2. 現在のレート制限の設定と使用状況
3. 回避策の提案（リトライ戦略、トークン分散など）

期限: 本日中
報告: 調査結果と推奨対策をまとめて返答してください。
途中で重大な発見があれば即座に報告してください。""",
    intent="question"
)
```

### 예시 3: 리뷰 요청

**나쁜 지시:**
```
send_message(
    to="carol",
    content="コード見ておいて。",
    intent="question"
)
```

**좋은 지시:**
```
send_message(
    to="carol",
    content="""認証モジュールのコードレビューをお願いします。

対象ファイル: ~/project/auth/token_manager.py（新規追加）
確認観点:
- セキュリティ上の懸念がないか（トークンの保存・失効処理）
- エラーハンドリングの網羅性
- 既存の auth_handler.py との整合性

期限: 明日（2/16）午前中
報告: 問題なければ「LGTM」、修正点があれば具体的な箇所と理由を返答してください。""",
    intent="question"
)
```

## 작업 위임 패턴

### 패턴 1: 단발 작업(부하에게 위임)

한 번만 하는 작업을 **직속 부하**에게 위임할 경우 `delegate_task`을 사용한다. 작업 큐에 추가되고 진행 상황을 `task_tracker`로 추적할 수 있다.

필수 파라미터: `name`(위임 대상), `instruction`(지시 내용). 선택: `summary`(한 줄 요약), `workspace`, `acceptance_criteria`, `model`. 마감일이 있으면 `instruction` 본문에 기재한다.

```
delegate_task(
    name="alice",
    instruction="""API仕様書（/shared/docs/api-spec.md）にv2.1の変更点を反映してください。

変更内容:
- /api/users エンドポイントにページネーションパラメータ追加
- レスポンスに total_count フィールド追加
- 変更の詳細: /shared/docs/changelog-v2.1.md を参照

完了したら返答をお願いします。""",
    summary="API仕様書 v2.1 反映"
)
```

### 패턴 1b: 단발 작업(동료·비부하에게 요청)

부하가 아닌 상대에게 요청은 `send_message`로 `intent="question"`를 지정한다.

```
send_message(
    to="alice",
    content="""【依頼】ドキュメント更新

API仕様書（/shared/docs/api-spec.md）にv2.1の変更点を反映してください。

変更内容:
- /api/users エンドポイントにページネーションパラメータ追加
- レスポンスに total_count フィールド追加
- 変更の詳細: /shared/docs/changelog-v2.1.md を参照

期限: 2/16 15:00
完了したら返答をお願いします。""",
    intent="question"
)
```

### 패턴 2: 지속 작업(정기 작업 위임)

하트비트나 cron에 포함해야 할 정기 작업을 지시하는 패턴. 지속 작업은 `delegate_task`의 대상이 아니므로 `send_message`로 `intent="question"`을 지정한다.

```
send_message(
    to="bob",
    content="""【継続依頼】日次のログ監視

今後、毎日午前中にアプリケーションログの異常チェックを行ってください。

対象: /var/log/app/error.log
確認内容:
- 過去24時間のERROR/CRITICALレベルのログ件数
- 新規パターンのエラーが出ていないか

報告ルール:
- 異常なし → 報告不要
- ERROR 10件以上 or 新規パターン → 即座に私に報告
- 毎週金曜に1週間のサマリーを報告

この内容をあなたのハートビートチェックリストに追加してください。""",
    intent="question"
)
```

### 패턴 3: 단계적 작업(마일스톤 포함)

큰 작업을 단계로 나누어 위임하는 패턴. 부하라면 `delegate_task` 사용. 동료·비부하에게 요청은 `intent="question"`.

```
send_message(
    to="carol",
    content="""【依頼】新機能の設計と実装（3段階）

ユーザー通知機能の追加をお願いします。

Phase 1（2/17まで）: 設計
- 通知の種類（メール/Slack/アプリ内）と優先度の定義
- データモデルの設計案
→ 設計案を返答してください。私が承認後にPhase 2に進んでください。

Phase 2（2/20まで）: 実装
- 承認された設計に基づいて実装
- テストコード含む
→ 完了したら返答してください。

Phase 3（2/21まで）: ドキュメント
- API仕様書と利用ガイドの作成

各Phase完了時に返答をお願いします。
Phase間で方針に迷う場合は相談してください。""",
    intent="question"
)
```

## 후속 조치(진행 상황 확인) 패턴

### 마감일 전 확인

진행 상황 확인은 질문에 해당하므로 `intent="question"`을 지정한다.

```
send_message(
    to="alice",
    content="""売上データ集計の進捗を確認します。
期限は明日（2/18）17:00ですが、順調に進んでいますか？
ブロッカーがあれば教えてください。""",
    intent="question"
)
```

### 마감일 초과 시 후속 조치

```
send_message(
    to="bob",
    content="""ログ監視の調査結果について確認です。
本日中が期限でしたが、状況はいかがですか？
困っている点があれば教えてください。必要に応じて期限を延長します。""",
    intent="question"
)
```

### 결과물 수령 후 피드백

수정 요청은 위임에 해당하므로 부하라면 `delegate_task` 사용. 동료·비부하에게 요청은 `intent="question"`를 지정한다.

```
send_message(
    to="carol",
    content="""設計案を確認しました。全体的に良い方向です。

修正をお願いしたい点:
1. 通知の再送ロジックに指数バックオフを追加してください
2. 通知テンプレートのi18n対応を設計に含めてください

上記を反映した修正版を2/18までにお願いします。""",
    intent="question"
)
```

## 에스컬레이션 판단 기준

스스로 처리할지, 상급자에게 에스컬레이션할지의 판단 기준.

### 스스로 처리해야 할 상황(에스컬레이션 불필요)

- 절차가 명확하고 자신의 권한 내에서 완결되는 작업
- 경미한 오류로, 알려진 복구 절차가 있는 경우
- 부하의 질문으로, 자신의 지식으로 답변 가능한 경우
- 작업의 우선순위가 명확하고 판단에 망설임이 없는 경우

### 에스컬레이션해야 할 상황

- MUST: 자신의 권한을 넘는 판단이 필요한 경우(예: 외부 API 연동 방침 변경)
- MUST: 여러 부서에 영향을 주는 인시던트가 발생한 경우
- MUST: 마감일을 맞출 수 없음이 확실해진 경우
- SHOULD: 예상 밖의 상황에서 정답이 여러 개이고 판단이 어려운 경우
- SHOULD: 부하의 에스컬레이션을 받았지만 자신도 해결할 수 없는 경우

### 에스컬레이션 전달 방법

에스컬레이션은 상급자에게 보고·판단 요청이므로 `intent="report"`을 지정한다. 긴급 시에는 `call_human`도 검토한다.

상급자가 Anima인 경우 `to`에 Anima 이름을 지정. 인간 관리자에게 보낼 경우 `config.json`의 `external_messaging.user_aliases`로 설정한 별칭 이름을 `to`에 지정하면 Slack/Chatwork 등의 외부 채널로 자동 배포된다.

```
send_message(
    to="manager",
    content="""【エスカレーション】デプロイパイプラインの障害

状況: GitHub API のレート制限により自動デプロイが12時間停止中
影響: 本日リリース予定の機能（v2.1）がデプロイできない
試した対策: リトライ間隔の延長、キャッシュの活用（いずれも効果なし）
判断が必要な点: 別のGitHubトークンを発行するか、手動デプロイに切り替えるか

ご判断をお願いします。""",
    intent="report"
)
```

## 지시 템플릿

다음 템플릿을 `send_message`에서 사용할 때는 `intent`을 적절히 지정할 것(요청=question, 보고=report, 질문=question. 부하에게 작업 위임은 `delegate_task` 사용).

### 범용 작업 요청 템플릿

```
【依頼】{タスク名}

{背景・目的（1-2行）}

作業内容:
- {具体的な作業1}
- {具体的な作業2}

成果物: {何をどこに出力するか}
期限: {日時}
報告: {完了時/途中経過/問題発生時のどれか}
```

### 조사 요청 템플릿

```
【調査依頼】{調査テーマ}

背景: {なぜこの調査が必要か}

調査してほしいこと:
1. {調査項目1}
2. {調査項目2}
3. {調査項目3}

期限: {日時}
報告: 調査結果と推奨アクションをまとめて返答してください。
```

### 리뷰 요청 템플릿

```
【レビュー依頼】{対象の名前}

対象: {ファイルパスまたはリソース}
確認観点:
- {観点1}
- {観点2}

期限: {日時}
報告: 問題なければ「LGTM」、修正点があれば具体的に返答してください。
```
